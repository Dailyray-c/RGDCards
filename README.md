# 红心大战 · Hearts　/　拱猪 · Gongzhu　/　斗地主 · DDZ

> 当前版本：**v10** —— 三种玩法 + 联机对战 + 统一控件体系（2026-09-26）。
> 历史迭代记录（第 6 ~ 9 轮）见下文。

一个纯原生 JavaScript 实现的网页版纸牌游戏，**无构建步骤、无框架、无运行时依赖**，
双击 `index.html` 即可游玩，也可直接托管到 GitHub Pages 在线打开。

| 玩法 | 人数 | 目标 |
|---|---|---|
| 红心大战 | 4 人 | 少收罚分，累计分**最低**者获胜 |
| 拱猪 | 4 人 | 猪 / 羊 / 变压器 + 亮牌翻倍，累计分**最高**者获胜 |
| 斗地主 | 3 人 | 叫分抢地主 + 底牌，先出完牌的一方获胜（可联机或 AI 补位） |

另有**联机对战**：房间码 / 扫码邀请，跨设备同桌出牌。需在「联机设置」里各自填入
Upstash REST 凭据（详见 `联机配置说明.md`；凭据只存本机，仓库里的 `net-config.js` 是空占位）。

## 文件结构

```

gongzhu.js        拱猪规则引擎（纯逻辑，不碰 DOM）
ddz.js            斗地主规则引擎（纯逻辑，不碰 DOM）
players.js        玩家抽象 + 三档难度 AI
app.js            状态机 + 渲染 + 交互（模式感知）
collect-anim.js   收牌飞行动画（FLIP）
```

> ⚠️ `hearts.js` / `gongzhu.js` / `ddz.js` 都是**经典 script** 加载，共享全局作用域。
> 三者都整体包在 IIFE 里，否则顶层 `const SUITS` / `RANKS` / `RANK_VALUE` 同名冲突，
> 后加载的模块会整块不执行（详见"开发过程中修掉的真实 Bug"第 9 条）。

**方式二**（推荐，避免个别浏览器的本地文件限制）：
```bash

# 访问 http://127.0.0.1:8331/index.html
```

保存几分钟后即可通过 `https://<用户名>.github.io/<仓库名>/` 访问。

## 规则实现

采用标准红心大战规则，附加可切换的满贯变体。

| 项目 | 规则 |
|---|---|
| 罚分 | 每张红心 1 分，黑桃 Q 13 分，共 26 分 |
| 首墩首引 | **第一墩由持梅花 2 者首引，且他只能出梅花 2** |
| 必须跟花色 | 手中有首引花色则必须跟出 |
| 首轮禁红心 | 第一墩不能出红心，除非手中只剩红心与黑桃 Q |
| 首轮禁猪 | 第一墩不能出黑桃 Q，同上例外 |
| 首引禁红心 | 每墩首引不能出红心，除非手中只剩红心 |
| 收墩 | 只看首引花色，最大者收下该墩所有罚分 |
| 满贯 | 一人独收 26 分。默认自己 −26 分，可切换为其余三家各 +26 |
| 终局 | 任一家累计达 100 分结束，总分最低者获胜 |
| 传牌 | 向左 → 向右 → 对家 → 不传，循环 |

**例外处理要点**：首轮中红心与黑桃 Q 地位平等。当手中除这两者外再无他牌时，两者一并解禁，
不会出现"放开了红心却仍禁着猪"的错误（该分支有专门的单元测试覆盖）。

**首墩首引的约束优先级**：`mustLeadClub2` 判定在最前，只要持 C2 就返回 `[C2]` 单张，
优先于"首轮禁红心/禁猪"。异常情况下（构造的牌局里没人持 C2）退化为常规首引，
避免 `legalCards` 返回空数组导致整局卡死。

## 拱猪规则（第 7 轮新增）

顶栏 `红心大战 / 拱猪` 分段控件切换模式。切换后牌桌、渲染、AI 全部跟随，
**共享同一份对局进度**（累计分、局数都保留）。

### 分值表

| 牌 | 分值 | 说明 |
|---|---|---|
| 猪 ♠Q | **−100** | 谁收到谁扣 |
| 羊 ♦J | **+100** | 谁收到谁得 |
| 变压器 ♣10 | 自身 0 分 | **持有者本局总分 ×2**；若本局无分则记 **+50** |
| 红桃 A | −50 | |
| 红桃 K | −40 | |
| 红桃 Q | −30 | |
| 红桃 J | −20 | |
| 红桃 10 ~ 5 | −10 每张 | |
| 红桃 4 / 3 / 2 | 0 | **无分值** |
| 其余牌 | 0 | |

红桃合计 **−200** 分。

### 特殊成就

| 成就 | 条件 | 分值 |
|---|---|---|
| 满红 | 一人独收 13 张红桃 | **+200**（整段替换红桃扣分） |
| 满贯 | 同一人**同时**收齐满红 + 猪 + 羊 | **+400**（整段替换，猪的 −100 与羊的 +100 已被吸收） |

⚠️ **满贯是"整段替换"而不是"叠加"**。写成 `满红200 − 猪100 + 羊100 + 400` 会得到 500，是错的。
实现里走 `total = GRAND_SLAM_BONUS` 并清空明细数组，只保留一条「满贯」记录。

### 与红心大战的规则差异

| 项目 | 红心大战 | 拱猪 |
|---|---|---|
| **传牌** | 发牌前向左/右/对家传 3 张 | **没有传牌**，发牌后直接开打 |
| 首墩首引 | 强制梅花 2 | 强制梅花 2（**相同**） |
| 必须跟花色 | 是 | 是（**相同**） |
| 首墩禁红心 | 禁止 | **不禁止** |
| 首墩禁猪 | 禁止 | **不禁止** |
| 首引禁红心 | 禁止 | **不禁止** |
| 收墩判定 | 只看首引花色 | 只看首引花色（**相同**） |
| 终局 | 累计达阈值，**低分获胜** | 累计达阈值，**高分获胜** |
| 默认阈值 | 100 | **−1000**（可自定义） |

### 亮牌（分数翻倍）

开局**发牌前**进入亮牌阶段。可亮 **猪 ♠Q / 羊 ♦J / 变压器 ♣10 / 红桃 A** 四张。
亮出的牌被人收到时**分数 ×2**（负分翻倍更亏，正分翻倍更赚）。
AI 也会按难度决策是否亮牌：入门档仅在特定条件亮猪；熟练/高手档按套长与大牌判断，
高手档额外支持亮变压器。

### 计分与结算

- **两阶段结算**：先弹「本局明细」（逐张列出 猪 / 羊 / 变压器 / 红桃 / 成就 的贡献与是否翻倍），
  点确认后才把本局分累加进总分并推进局数。
- **变压器**：持有者本局总分 ×2；若本局恰好 0 分，则记 +50。
- **终局**：任一家累计分 ≥ 自定义阈值（默认 **−1000**）即结束，**累计分最高者获胜**。

### 局内实时分值（第 8 轮新增）

侧栏计分板的「本局」列**不等结算才出数**，由 `GONGZHU.liveScore(cards, sold)`
实时计算已收牌堆的当前分值，提前体现：

- **亮牌 ×2**：亮出的猪被收到 → 立刻显示 −200（而不是 −100）
- **变压器 ×2**：持有变压器且有分 → 显示翻倍后的分
- **变压器无分 +50**：持有变压器且当前 0 分 → 显示 **+50**

返回 `{ total, base, doubled, transformerEmpty }`：
`base` 是未翻倍的原始值，`doubled` / `transformerEmpty` 供 UI 决定文案。

> ⚠️ `liveScore` 与 `settleRound` 是**两条独立的计算路径**，必须保持公式一致。
> 单元测试专门覆盖了两者的一致性（含「亮牌相抵为 0 时变压器按无分 → +50」这类边界）。

### 出局进度条（第 8 轮新增）

拱猪计分板对**累计负分**的家显示一条进度条，表示「欠分距离出局线还有多远」：

| 进度 | 档位 | 颜色 |
|---|---|---|
| < 50% | `is-gz` | 中性灰（还有余量） |
| ≥ 50% | `is-warn` | 橙 |
| ≥ 80% | `is-danger` | 红 |

**正分与 0 分不渲染进度条** —— 正分是在赢分，画成"快出局了"会误导。

> ⚠️ 三档配色**一律避开绿色**。拱猪里绿色 = 正分 / 安全，
> 用绿色画"欠分进度条"会让人误读成"很安全"（第 8 轮就踩过这个坑）。

### ⚠️ 分数守恒的边界（不是 Bug）

拱猪总分**近似**守恒，但有三类规则特性会合法地破坏严格守恒：

1. **变压器**放大持有者分数，凭空注入差值
2. **满红 +200 / 满贯 +400** 是奖励性注入
3. **亮牌**被收到的牌 ×2，没有对应的负值补偿

因此**严格守恒只在「无满红 + 无亮牌 + 移走变压器」的干净子集上成立**，
常量 = **−200**。测试就按这个口径断言（900 局自对弈全部通过）。

## 架构设计

### 规则与界面完全分离

`hearts.js` / `gongzhu.js` 都是不依赖 DOM 的纯函数模块，可同时在浏览器和 Node 下运行：

```js
// hearts.js
legalCards(hand, { leadSuit, isFirstTrick, mustLeadClub2 })  // 计算合法牌
trickWinner(plays, leadSuit)                                 // 判定收墩者
settleRound(collected, moonSelf)                             // 本局结算

// gongzhu.js
legalCards(hand, { leadSuit, mustLeadClub2 })                // 拱猪无首墩禁区
settleRound(collectedCards, { sold })                        // 返回 {deltas, details, mooner, slammer}
ranking(players)                                             // 降序（高分获胜）
```

### 模式切换的实现：`H` Proxy 兼容层

`app.js` 里有 84+ 处 `H.xxx` 调用。为了不逐个改，用 Proxy 让它们自动跟随模式：

```js
const RULES_BY_MODE = { hearts: HEARTS, gongzhu: GONGZHU };
function rule() { return RULES_BY_MODE[state.mode] || HEARTS; }
const H = new Proxy({}, {
  get: (t, k) => rule()[k],
  has: (t, k) => k in rule(),
});
```

于是原有的 `H.legalCards(...)`、`H.settleRound(...)` 一处不改就能双模式工作。
仅少数语义不同的地方（结算、渲染、提示文案）显式走 `isGongzhu()` 分支。

**双份收牌记录**：`state.collected`（分数累加值，侧栏用）与 `state.collectedCards`
（收到的**牌面数组**）。拱猪结算判满红/满贯/亮牌/变压器**必须知道具体牌面**，
光有累计分是算不出来的。

### Player 抽象：为对战模式预留

所有出牌方都实现同一接口，核心逻辑只认接口不认实现：

```
Player（基类）
├── HumanPlayer   真人，出牌经由 Promise 等待 UI 提交
└── AIPlayer      AI，三档难度
```

将来要加**本地双人**或**联机对战**，只需新增一个控制器实现 `chooseCard(legal, ctx)`，
规则引擎、渲染、计分全部零改动。

### AI 三档难度

难度差异不是简单调随机数，而是在决策深度上分层：

| 档位 | 出牌策略 | 传牌策略 |
|---|---|---|
| 入门 | 能跟花色、随机出小牌 | 只看是否猪/红心，35% 概率判断失误 |
| 熟练 | 避开心张、追猪、判断满贯时机 | 完整风险模型（点数 × 套长） |
| 高手 | 上述 + 记牌、推断断门、残局穷举 | 额外避免把手牌传成"空心" |

**实测强度**（各档 400 局对战入门档）：

| 档位 | 人均罚分 | 对入门档优势 | 满贯把握度 |
|---|---|---|---|
| 入门 | 7.50 | — | 1 次 / 200 局 |
| 熟练 | 5.73 | 24% | 8 次 / 200 局 |
| 高手 | 4.85 | 35% | 26 次 / 200 局 |

### AI 双规则分流

`players.js` 通过 `setRules('hearts' | 'gongzhu')` 切换内部规则表 `R`。
两套规则的**分值量级与符号完全相反**（红心大战里红桃是正分要躲，拱猪里红桃是负分也要躲，
但羊是 +100 要抢），所以每个决策函数都按 `R === GONGZHU_RULES` 分支：

| 函数 | 拱猪分支的行为 |
|---|---|
| `discardScore` | 变压器 −5、猪 200、羊 −30、红桃 `abs(pts)+20`、无分牌用点数 |
| `shouldTakeTrick` | `points > 0` 才收（正分照收，负分要躲） |
| `prefersDump` | `dumpRisk >= 120 && winCost <= 10` |
| `chooseDiscard` | 本墩注定归我且带负分时塞大红桃，避免垫猪 |
| `chooseFollow` | pts>0 抢、pts<0 躲、空墩出最小 |
| `chooseLead` | 优先"贱卖"负分牌，避开猪 |
| `passRisk` | 羊 −1000、变压器 −800、猪 +1000（**符号与红心大战相反**） |
| `choosePassEasy` | 羊/变压器硬性不外传 |
| `pickNormal` | 用 `simulateTakeAll` 精确比较收墩收益 |
| `solveEndgame` | 符号修正 `s += gz ? immediate : -immediate` |
| `chooseSellCards` | 亮牌决策（入门仅特定条件亮猪；高手额外支持变压器） |

**实测强度**（固定座位对抗局，高手 vs 入门）：

| 阵营 | 人均得分 | 胜率 |
|---|---|---|
| 高手 | **−51.36** | **59.4%** |
| 入门 | −88.96 | 40.6% |

行为校验：高手传猪 **598 次**，送出羊 / 变压器 **0 次**（把资产留住、把负债甩出去）。

> ⚠️ **为什么不能比"四家总分"**：拱猪总分近似守恒（−200 ~ −250），
> 强者只是把罚分**转嫁**给弱者，四家加起来几乎不变。
> 最初用总分做口径，跑出"高手 −85160 vs 入门 −84410"几乎无差异的假结论。
> **守恒型游戏必须用固定座位对抗局比较阵营得分**。

## 开发过程中修掉的真实 Bug

1. **全局标识符冲突**：`players.js` 与 `app.js` 都在顶层用 `const H` 声明，同页加载时
   触发 `Identifier 'H' has already been declared`，导致后加载的脚本整个不执行、页面完全空白。
   修法：两个文件都包进 IIFE。

2. **首轮解禁逻辑不对称**：手中只剩 `H5 H9 SQ` 时，原实现只放开红心却仍禁着猪，
   玩家会陷入"只能出红心"的错误状态。修法：红心与猪一并放开，并补了对应测试。

3. **出牌位标签被反复清空**：座位标签写在 slot 内部，而 `renderTrick()` 每次都重写
   slot 的 `innerHTML`，第二次渲染后 `$('lbl1')` 变成 `null` 导致渲染链路中断、
   整手牌不显示。修法：把标签移出 slot，改用独立的 `.slot-cell` 结构。

4. **出牌区牌面闪烁**：`renderTrick()` 原本每次都把 4 个 slot 的 `innerHTML` 清空重建，
   已经落桌的牌被销毁重建、入场动画反复重播，视觉上就是"闪一下"。
   修法：改为**增量渲染**——用 `renderedTrickKeys` 记录已经渲染过的 `座位:牌` 键，
   只追加新落桌的牌，旧节点原地保留；清空只在整墩结束后做一次。

5. **断门时提示词误导**：玩家已无该花色、垫牌被拒时，原提示仍说"本墩须跟出 X"。
   修法：先判断手里是否真有该花色，只有确实有时才提示"必须跟出"。

6. **小屏下牌面数字重叠**：手牌用固定 `-18px` 叠压，但小屏卡片只有 48px 宽，
   叠压后单牌仅露出 30px，右侧牌的左上角点数正好压在左侧牌的右下角点数上，
   两个数字糊成一团。修法：叠压量改为相对卡宽 `calc(var(--card-w) * -N)`，
   并在 ≤900px 隐藏右下角反向角标，从根上消除接缝处的数字叠加。

7. **小屏媒体查询里的固定 px 覆盖了百分比尺寸**：`@media (max-width:720px)` 中
   写了 `.slot .card .card-suit-big { width: 20px; height: 20px }`，把百分比尺寸

### ⭐ 额外修复：并发对局循环导致状态错乱

**症状**：控制台 `Cannot read properties of undefined (reading 'hand')` / `(reading 'player')`。

**根因**：`playLoop()` 是 `async`，`await` 期间交出控制权。若旧循环未结束就触发新一轮
（典型场景：**结算动画还没播完就点「新的一局」**），两个循环同时推进同一份 `state`
—— 一个清空了 `state.players` / `trickPlays`，另一个正在读
`state.players[seat].hand` 或 `trickPlays[0].player` → 抛错且牌局彻底错乱。

**修法**：引入 `runId` 代际标记，所有 `await` 返回后校验代际，过期循环自行退出。

```js
let runId = 0;

async function playLoop(myRun) {
  while (state.trickIndex < 13) {
    if (myRun !== runId) return;      // 过期循环 → 静默退出
    await playTrick(myRun);
    if (myRun !== runId) return;
    if (state.phase !== 'playing') return;   // 结算/切模式也会终止循环
  }
  endRound();
}
```

`playTrick(myRun)` 里每次 `await` 后同样校验；另外补了两道防御：
- 出牌前 `if (!state.players[seat].hand.includes(card)) return;`（牌已不在手中）
- 收墩前 `if (state.trickPlays.length !== 4) return;`（桌面被清空）

`startRound()` 首行 `runId++`；`beginPlay()` 用 `const myRun = ++runId`。

**通用教训**：任何"异步循环 + 可被用户重新触发"的组合，都需要代际标记。
只靠 `busy` 标志位不够 —— 它挡得住重入，挡不住**在途的旧循环**继续持有过期引用。

只验单个分值或单张牌的存在性，是抓不到"少了 39 张"这种 bug 的 ——
本轮的回归锁定测试就是按这个原则补的（见下）。

### 4. 顺带修复：`setMode()` 未作废在途循环

第 8 轮引入了 `runId` 代际标记来防止并发对局循环互相干扰，但**漏了一个调用点**：
`setMode()` 会把 `state.players` 清空为 `[]`，却**没有递增 `runId`**。

后果：切模式时若旧循环正卡在 `await`（AI 思考 / 等玩家出牌）上，
它醒来后仍会去读 `state.players[seat].hand` → `undefined.hand`
→ 抛 `TypeError: Cannot read properties of undefined (reading 'hand')`。

**两层修复**：

```js
// ① 根治：setMode() 首部作废所有在途循环
function setMode(mode) {
  runId++;                // ← 关键
  state.players = [];
  ...
}

// ② 兜底：playTrick 出牌前先判断玩家对象还在不在
const pl = state.players[seat];
if (!pl || !pl.hand.includes(card)) return;
```

另修一处 **TDZ 风险**：`let runId` 原本声明在意 1011 行，却被 153 行的
`setMode()` 使用。运行时侥幸可用（`setMode` 只在脚本求值完成后才被调用），
但属于**暂时性死区**，很脆弱。已把 `let runId = 0` 上移到 state 定义之后、
所有使用者之前。

> **规则**：每一个会**清空 / 重建牌桌**的入口都必须 `runId++`
> —— `startRound()` / `beginPlay()` / `setMode()`（本轮补上）。

### 回归锁定：为什么断言"总量"而不是"单点"

`_test_gongzhu.js` 新增的 **[13] 收墩完整性** 组，核心是这条不变量：

- 用真实 `legalCards` / `trickWinner` 驱动一副完整牌，实走 13 墩，
  按「赢家收走桌面全部 4 张」归集 → **断言归集总量恒为 52**
- 反例对照：同一墩下"收 4 张"得 −50、"只收 1 张"得 0 → 断言两者**必须不同**
  （确保这条断言**具备捕获退化的能力**，而不是恰好都通过）
- 常量不变量：`4 × 13 = 52`（发牌）、`13 墩 × 4 张 = 52`（收墩）

**[14] 变压器与满红可达性** 组锁定次生影响：

- 洗牌 300 次，变压器 **100%** 在牌堆里
- 实走 50 局，变压器 **100%** 有归属（修复前仅 ~32%）
- 满红 / 满贯必须可达（+200 / +400）
- 对照：只收 12 张红桃**不判**满红、凑齐 13 张才判 → 漏 1 张即失效

这两组共 36 条断言，是防止收墩逻辑再次退化的**唯一保险**。

9. **【致命】`Identifier 'SUITS' has already been declared`**：加入 `gongzhu.js` 后，
   切到拱猪**完全无效**，`window.GONGZHU === undefined`，全部拱猪断言 FAIL。
   控制台报了一次 `Identifier 'SUITS' has already been declared` 之后，
   **`gongzhu.js` 整个文件一行都不执行**。
   根因：`hearts.js` 与 `gongzhu.js` 都是**经典 script** 加载（非 module），
   共享同一个全局词法作用域，两者顶层都声明了 `const SUITS` / `RANKS` / `RANK_VALUE`。
   修法：**两个文件都整体包进 IIFE**，只通过 `window.HEARTS` / `window.GONGZHU` 暴露入口。

   ```js
   (function (root) {
     'use strict';
     // ...全部逻辑...
     if (typeof module !== 'undefined' && module.exports) module.exports = GONGZHU;
     if (root && typeof window !== 'undefined') root.GONGZHU = GONGZHU;
   })(typeof window !== 'undefined' ? window : this);
   ```

   **体检命令**：`grep -n "^const \|^let \|^class " *.js`，同名出现在两个文件顶层 → 必炸。
   这类错误**不指向冲突的另一方文件**，只能靠"哪个脚本完全没生效"反推。

10. **满贯公式算成 500**：初版 `total = base - heartPart - pigPart + GRAND_SLAM_BONUS`，
    因 `base` 里已含 `sheepPart`，结果算出 500 而非 400。
    修法：满贯走**整段替换** `total = GRAND_SLAM_BONUS`（=400），并 `parts.length = 0`
    只留一条明细。用"满贯 + 变压器 = 800"这条用例才验证到位。

11. **红桃分值实现错误**：原实现按"2~9 均为 0 分、合计 −150"。
    实际标准拱猪是 **2/3/4 = 0、5~10 = −10**，合计 **−200**。
    修正后同步更新了全部 86 项断言。
    **教训**：规则类项目里"记错的规则"比"写错的代码"更危险——
    代码和测试会一致地错下去，只有用户实际游戏时才发现。

## 牌面设计

牌面采用**角标**布局，点数在最左上角、花色紧贴其下，右下角为 180° 反向对称角标：

```
┌──────────┐
│ 10       │   ← 点数在左上角（最先被看到的位置）
│ ♦        │   ← 花色紧随其下
│          │
│    ♦     │   ← 中央花色：居中 + 颜色加深，作主视觉
│          │
│       ♦  │
│       10 │   ← 右下角反向角标
└──────────┘
```

- 角标点数使用**固定行高**，避免 `10` / `J` / `Q` 等不同字宽把角标高度撑得不一致
- 中央花色**严格居中**（`top/left: 50%` + `translate(-50%,-50%)`），不透明度 `.78`
- 中央花色尺寸按卡片短边取百分比（桌面 56%、小屏 44%），因此 44px 手牌与 80px
  桌面牌能同比缩放；小屏单独取 44% 是因为卡片变小后 56% 会压到左上角标
- 梅花按参考图重绘为**三圆瓣 + 短柄**的矢量路径

手牌区固定**单行展示 13 张**：空间充足时正常间距排列，变窄时逐级收窄间距并施加负
`margin` 叠压，而不是折行（折行会出现一张牌孤零零掉到第二行）。

**叠压幅度的安全上限**：叠压太深会让右侧牌的左上角点数压到左侧牌的右下角点数上，
小屏下两个数字糊成一团。因此：

- 叠压量用 `calc(var(--card-w) * -N)` 相对卡宽计算，窄屏卡片变小时同步变小
- ≤900px 时**隐藏右下角反向角标**（`.card-corner.br { display: none }`），
  从根上消除接缝处的数字叠加
- 悬停或选中的牌 `z-index` 提升到最上层，避免被右侧邻居遮住

实测各视口下单张牌的可见宽度与角标占位（余量均为正 = 不发生重叠）：

| 视口 | 卡宽 | 单牌可见宽 | 角标占位 | 余量 |
|---|---|---|---|---|
| 1440 | 44px | 48px | 14px | 34px |
| 1024 | 56px | 40px | 14px | 26px |
| 820 | 53px | 32px | 14px | 18px |
| 600 | 48px | 32px | 12px | 20px |

## 交互反馈

### 传牌阶段

- **选中态足够醒目**：选中牌背景由白转浅绿、描边加粗为强调色、叠加勾选标记，
  并轻微放大（`scale(1.03)`），与未选中的白底牌形成明确对比
- **不做向上弹出**：牌是紧密并排的，上弹会被相邻牌遮住反而看不清。
  选中反馈只靠「描边 + 底色 + 勾选标记 + 轻微放大」，层次清楚又不挡牌
- **明确告知传给谁**：弹窗顶部常驻「传出对象：AI 西」以及"本局向左传，你要把 3 张
  牌传给 AI 西"的完整说明
- 已选计数实时更新（`已选 2 / 3`），选满后给出可确认提示，超额点击时提示先取消一张
- 弹窗只构建一次 DOM，之后仅切换 class，避免每次点击重建节点造成闪烁

### 首引标记

每墩**第一张落桌的牌**会带上「首引」角标并加一圈强调色描边，方便一眼看出本墩是谁
开的头、该跟什么花色。

因为出牌区是**增量渲染**的，标记不能只在插入时设置一次——`syncLeadMarker()` 会在每次
渲染后统一校正，确保桌面上**有且只有**首引那张牌带标记（避免遗漏或残留）。

### 出牌提示

提示语按局面分三种，文案随「是否断门」改变：

| 局面 | 提示 |
|---|---|
| 首引 | `轮到你首引 · 不能出红心，可出 5 张` |
| 跟牌 | `轮到你出牌 · 必须跟出方块，且第一墩不能出红心和黑桃 Q（可出 2 张）` |
| **断门** | `你已没有方块，可以垫任意牌（6 张可选） · 垫牌时尽量避免红心` |

断门时还会按场面给出针对性提醒：手上有黑桃 Q 则提示"注意别把黑桃 Q 垫进去"；
本墩已有分数则提示"垫小牌即可"；全程只有红心时说明"只能出红心"。

### 节奏控制

AI 出牌的等待时间刻意放慢，避免一眨眼就轮到下一家：

| 环节 | 时长 |
|---|---|
| AI 思考 | 700 ~ 1100 ms |
| 出牌后到下一家 | 620 ms |
| 收墩前停顿 | 850 ms |
| 收墩后停顿 | 950 ms |

实测同一墩内 AI→AI 的落桌间隔平均 **1051 ms**（调整前约 260 ms）。

## 已知限制

- AI 的记忆是"本局内"的，跨局不累积对手习惯
- 高手的残局穷举只在手牌 ≤ 4 张时启用，更深的状态仍走启发式
- 传牌时不能指定"传给特定对手"，只按固定方向轮换（标准规则本身如此）
